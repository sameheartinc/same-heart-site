# Same Heart — Architecture Plan: Radio, Identity, Collective Knowing, Communities, and Curation

This is the plan for five things asked for in one go: the transmit sound and graphic, an allocated identity number per user, RSS-based "collective knowing" (and whether that costs money), a Community/forum system where people can build their own spaces within Same Heart, and a curation engine that connects people to experiences, to content, and eventually to each other — with character-building layered on top. Two of the five are small and self-contained enough to build immediately; this update ships both. The other three are real systems that depend on each other in specific ways, so this plan sequences them rather than trying to build all three at once.

## What shipped in this update

The transmit sound and the Signal Number were both buildable today, with no dependency on anything else, so they're done rather than just planned.

Submitting a Star Day now triggers a short "transmit" moment: a burst of filtered white noise that settles into a clean tone, synthesized live with the Web Audio API in `lib/transmit.ts` — no audio file to host or license. Alongside it, three gold rings expand outward from a center point with "Signal locked" underneath, in `app/star-day/page.tsx`. It respects `prefers-reduced-motion`, and it only plays after the Supabase write actually succeeds, so a failed submit still shows the normal error message instead of a false "locked" moment. `playTransmitSound()` is a standalone function specifically so the same beat can be reused anywhere else a send/submit moment deserves one — posting in the Community forum being the obvious future case.

Every profile now also carries a Signal Number: a permanent, sequential identity number (`Signal No. 000001`, `000002`, and so on) shown on the Hub under the designation. This is deliberately a separate concept from `designation`, which is derived from birth date and repeats across anyone born on the same day — Signal Number is unique per account and ordered by signup. It's implemented as a Postgres `bigserial` column, so the database handles the counting; the app code just reads it. The one honest caveat, documented in `supabase/schema.sql` and the README, is that accounts created before the migration runs get backfilled in Postgres's internal row order rather than guaranteed literal signup order — from the moment the migration runs forward, ordering is exact.

## Collective knowing: RSS feeds, and whether that costs money

The direct answer: pulling RSS/Atom feeds is free. Any site that publishes a public feed can be fetched with a plain HTTP request — no API key, no per-fetch charge, no vendor in the middle. What can cost money is adjacent to that, not the fetching itself: running the polling frequently enough and across enough feeds that it becomes a real compute cost (not a concern at the scale Same Heart is at), or paying for a *curated aggregator* service like a commercial news API that indexes thousands of sources for you instead of you hand-picking them, or paying to run each article through an LLM for summarization or categorization. None of those are required to get collective knowing working — they're upgrades to consider later if hand-picked feeds stop being enough.

The plan is to hand-curate a starting list of feed sources rather than pay for an aggregator, since a hand-picked list also does a better job of matching Same Heart's voice than a generic news firehose would. A `feed_sources` table holds each feed's URL, a label, and a category; a scheduled job — a Vercel Cron trigger hitting a Next.js API route, running hourly or so — fetches each one with a small free library like `rss-parser`, deduplicates by the item's link or GUID, and writes new items into a `feed_items` table (title, link, published date, source, summary, image). From there the items need somewhere to surface — a simple chronological "Signal Feed" is enough for a first pass, with per-user filtering by interest becoming possible once the curation engine (below) exists to drive it. A lightweight feed-discovery tool — given a site's homepage URL, look for its `<link rel="alternate" type="application/rss+xml">` tag and pull the feed URL automatically — is a small, free addition if hand-adding feeds by URL becomes tedious, but isn't required to start.

## Communities: people building spaces within Same Heart

This is the largest of the five pieces, so it's broken into an internal sequence rather than one big build.

The data model is a `communities` table (id, slug, name, description, creator, created date) plus a `community_members` table (community, profile, role — owner, moderator, or member — and joined date) and a `community_posts` table for whatever gets shared inside a community. This mirrors the RLS pattern already in `supabase/schema.sql` for `profiles` and `log_entries`: people can read what they're a member of, write what they're allowed to, and a community's creator becomes its owner automatically the same way a new signup automatically gets a profile row today.

Letting people "design the page" for their community doesn't need a new system invented from scratch — `lib/skins.ts` already exists precisely for this: a small set of CSS-variable overrides that reskin a page without touching its structure. Generalizing that same mechanism so a community picks (or eventually customizes) its own look reuses proven code instead of building a second theming system alongside the first.

Seeing how many members are active right now is a presence problem, and Supabase already ships a Realtime Presence feature built for exactly this: a lightweight channel per community tracks who's currently connected, with no separate polling infrastructure or extra server to run. It's included in Supabase's existing plan at this scale, so there's no new cost to seeing live counts, just new code to wire it up.

Letting the space "explode with different people building different communities" means a `/communities` directory needs to exist alongside the communities themselves — a browsable, searchable list showing each community's name, member count, and current active count, so discovery doesn't depend on already knowing a community exists.

Inside this piece, the build order is: schema and create/list communities first, then join and leave with a membership list, then basic posts inside a community, then presence for live active counts, then per-community theming last, since theming is the least load-bearing part and benefits from the rest already working.

## Connecting hearts: curation, and character built from real activity

Recommending anything — content, communities, or eventually people — needs to know what someone actually did on the site, which means an event-tracking layer has to exist before curation can. An `interaction_events` table (profile, event type, what it was about, when) is the substrate: it logs clicks and visits across feed items, communities, skins, and whatever else earns a tag later. This is more granular than the anonymous, aggregate analytics the current `/privacy` page describes, so shipping this is also the trigger to go back and revise that page to describe per-account interaction history honestly, rather than letting the policy quietly fall out of date with what the site actually collects.

For the curation itself, the plan deliberately starts simple rather than reaching for machine learning on day one. Tag a small number of categories onto each piece of content and derive a per-user affinity score from a plain recency-weighted count of what they've clicked, no model required. Recommend whichever content best matches someone's current top tags. This is honest about what it is: a reasonable v1, not a personalization engine, and one that only gets more capable once real interaction history has had time to accumulate — which is exactly why `interaction_events` should start logging as early as possible, even before the curation logic that reads it is built.

One design decision worth locking in now, even though curation itself isn't built yet: the thing being curated shouldn't be hardcoded as "a feed item." Give each recommendable thing a `kind` field from the start — `article`, `community_post`, `experience`, and so on — sharing one tagging and scoring system instead of a separate one per content type. It costs nothing extra to design it this way now, and it's exactly what lets the far-horizon idea below slot into the same system later instead of needing a rebuild.

The character-building piece — "they build out their character within the same heart universe" — doesn't need a new core mechanic either. Standing, XP, archetype, and Skins already exist and already work this way; the plan is to extend that same system so activity in the new areas (posting in a community, engaging with curated content) earns XP and log entries the same way existing actions do today, rather than inventing a second progression system running alongside the first.

"Connect hearts" read literally — matching people to *other* people who share their interests, not just matching people to content — is real and worth building, but it's flagged as the last step in this whole plan on purpose. Matching content to a person is low-stakes if it's wrong; matching people to people gets uncomfortable fast if it's wrong, or if someone didn't expect to be "matched" at all. That one is worth an explicit conversation about what it should feel like before any of it gets built, rather than shipping a first guess.

## The far horizon: real-world solutions, robotics, and big-tech partnerships

There's something further out on the wishlist too: eventually, people on Same Heart can reach actual robots and automation doing real work, plugged into the leading edge of science, technology, and economic development — tracking real progress, surfacing real solutions, and eventually making them available through partnerships with big tech companies. Worth being precise about which part of that is a software problem and which part isn't, since they need very different kinds of work.

The software part is genuinely buildable, and it's already what the plan above is building toward without saying so directly. "Track progress" and "surface real-world solutions" is a curation problem at its core — the same tagged-content-plus-affinity system above, pointed at a different category of source. Nothing stops `feed_sources` from including research and economic sources instead of only culture and wellness ones later — arXiv listings, public economic indicators, and press feeds from research institutions are public and free to pull, the same way any RSS feed is. The `kind` field on recommendable content means a future "solution" or "service" listing is just another kind of item in the same system that already exists for articles and communities, not a parallel system bolted on. That's the fabric: a platform generalized enough from day one that this is an extension of what's there, not a rebuild.

The part that isn't a software problem is *access*. Actually putting a real robot, a real AI agent, or a real service from a big tech company behind a Same Heart account requires that company's API, a commercial agreement, and usually a fee or revenue split — none of which gets created by writing more code. That's a partnerships and business-development effort, running in parallel to the product work, not a phase that falls out of the architecture the way character-building or presence tracking do. The honest sequencing is: build the fabric now so it's ready to host this the moment a real partnership exists, and treat the partnerships themselves as separate work that isn't blocked on engineering, and doesn't get resolved by it either.

The "draws everyone in" part is the identity, community, and curation work already planned above — a platform people already want to be part of for its own reason, on its own timeline, well before any of this exists. That's what has to be true first for a later "access the frontier of science and technology through Same Heart" pitch to land on an audience that's already there, rather than needing to be built from nothing at the same moment.

## Build order, end to end

Transmit sound and Signal Number are done. Next up is collective knowing (RSS), since it's fully self-contained and its cron-plus-two-tables infrastructure gets reused later for curation. After that, the Communities core (schema, create, join, post) — deliberately after RSS rather than in parallel, since communities will likely want to reference or share feed items once both exist, and it's worth having one working content system before building a social layer on top of it. Presence (live active counts) and per-community theming layer onto Communities once its core is solid. `interaction_events` should start logging as soon as Communities and the feed both exist, even before curation logic reads it, since curation quality depends directly on how much real history has piled up by the time it's built. The curation engine (content and community recommendations) comes once there's a few weeks of that data to work with. Character-building expansion falls out naturally once the above exists, since it's mostly "award XP for the new activity types" rather than new design. People-matching comes last, and only after a direct conversation about how it should feel.

## Keys and Doors: the game board underneath the platform

Standing already answers one question well — how much has someone actually done. Keys are for a question Standing structurally can't answer, because it's a single ladder: not how much, but what *kind* of person someone has become on Same Heart. Two people can sit at the same Standing tier having lived completely different lives on the site — one who shows up every day without fail, one who barely visits but leaves behind five real, high-impact Exchange links, one who's quietly become the reason three different communities feel alive. Standing would flatten all three into the same number. Keys are the layer that keeps them legible as different people, which is the actual shape of the original idea — a game board with many paths, not one longer ladder. So the call here is to keep the two systems separate rather than merge keys into XP: Standing keeps measuring effort over time, keys measure the shape of that effort, and neither one is allowed to quietly become the other.

That means keys are earned, never spent and never decayed. Once a color is yours, it's permanent — a record of a real thing you did, not a resource to manage. That's also what makes them worth being hard to get: there's no way to buy back a key you let lapse, so the only way to hold one is to have actually lived the behavior it represents.

Ten colors, ten different shapes of engagement, each one mapped to something the site can already measure or can measure with a small, honest addition — not ten flavors of the same "do more stuff" loop. Red is presence: a real return streak, meaning two real weeks of actually showing up on separate days, not a lucky run of logins in one sitting — it reuses `current_streak` and `longest_streak`, already tracked in `profiles`. Blue is breadth in the Commons: posting or replying across several different communities rather than living in just one, which rewards someone who's actually out exploring the space instead of camping a single thread. Green is real-world impact through the Exchange: a handful of transmissions that score well against the world-issues rubric already scoring every submission in `app/api/exchange/transmit/route.ts` — this one specifically punishes spam volume, since it's an average score across submissions, not a raw count. Yellow is engagement with the Signal — noticing and acting on real news, which needs a small new instrumentation layer (tracking that someone opened or reacted to a Signal item) that doesn't exist yet, so it's a second-phase key rather than a first one. Purple is self-knowledge — someone who keeps coming back to their own Star Day and Path data and goes deeper into it over time, which points at a future feature (a fuller archetype reading, unlocked by that attention) rather than reusing something that exists today. Pink is reciprocity — not how many replies someone writes, but how many of their replies get replied back to, which measures real two-way relationship rather than one-way broadcasting. Magenta is origination — founding a community that other people actually keep using, which rewards starting something that outlives your own attention on it. Indigo is real curiosity about the site itself, measured by sustained, varied use of the Commons Guide across different topics rather than one repeated question. Black is the meta-key, deliberately the hardest: it's only earned by already holding a real number of the other keys at once, which is the site's way of saying breadth and depth together is rarer than either alone. White is tenure and legacy — real account age carried alongside sustained good standing, not just "been here a while," and it's the one key that reaches back into the founding sequence already built into `/login` rather than pointing at something new.

What a door actually grants follows one rule, on purpose: doors only ever add a new capability, they never take away something that's currently free. Community creation, for instance, is already open to any signed-in person in the current schema — a key system that gated it later would be quietly taking back something people already have, which is exactly the kind of bait-and-switch this platform shouldn't do to the people who showed up early. So each door unlocks something genuinely new instead. Holding Red surfaces a live view of who else is actually present right now — you've proven you show up, so you get to see the room. Holding Blue lets someone choose a personal accent color that marks their posts and replies across the Commons, the same idea as the tagline color feature just shipped for the Exchange, but chosen rather than random, and earned rather than open to everyone. Holding Green unlocks a personal "impact history" page compiling every transmission someone's sent and what it actually scored — a keepsake of real-world contribution, not a leaderboard. Holding Yellow lets someone submit a source or topic suggestion that actually feeds the Signal's fetch list, which is real influence over what the whole platform sees, not just what one person sees. Holding Purple reveals a deeper layer of someone's own Star Day reading, for their eyes only. Holding Pink unlocks the ability to form a small persistent private group with people someone's already built real back-and-forth with — the first real relationship feature on the platform, earned rather than given by default. Holding Magenta gives a founder's flair on the community someone built and a featured rotation slot in the `/communities` directory once that exists. Holding Indigo extends how much the Guide remembers in a conversation and lets someone ask it about real aggregate site trends instead of only their own activity. Holding Black is the one purely cosmetic reward on this list, and deliberately so — a visible mark on someone's profile or ship that reads as rare across the whole site, because at that tier the achievement is the whole point. And holding White carries a permanent "early signal" mark tied to someone's real join date, plus the option to write one welcome note that gets shown to brand-new arrivals during the founding sequence — someone who's been here from early on gets an actual voice in how new people are greeted.

Holding all ten is the real endgame, and it's the one place this system should grant something beyond features: genuine light-touch influence over the platform itself. Someone who's proven breadth, depth, real-world impact, reciprocity, origination, curiosity, and tenure all at once has earned more than a badge — they've earned being asked. That could mean the ability to nominate a new World Issue category for the Exchange's scoring rubric, a standing invitation to be asked for feedback before a real feature ships, and a permanent place on an actual page listing everyone who's done it. That's "different levels of control and advancement... the ability to grow your information amongst others" read as literally as it can be built: the people who've engaged the widest and the longest get an actual hand in shaping what the platform becomes next, not just a bigger number next to their name.

Underneath all of it, the shape is simple on purpose. A `profile_keys` table (profile, color, earned date) is the only new state — insert-only, nothing ever removed, matching the "hard to get and permanent once earned" idea directly. Doors themselves don't need their own table: a door is just "does this profile hold this color," checked at the moment it matters, which avoids a second source of truth drifting out of sync with the keys themselves. Earning a key isn't something the client ever decides — a scheduled job evaluates the real thresholds against real data and inserts newly-earned keys itself, the same shape as the hourly Signal fetch already running as a Vercel Cron job, so this isn't new infrastructure, it's the same infrastructure pointed at a new question. Each newly-earned key also writes a `log_entries` row, so it shows up in someone's own history the same way everything else earned on the site already does. And because a key is a much richer signal than a single XP number — it says what someone actually likes doing, not just how much they've done — this is exactly the kind of interaction history the curation engine described earlier in this plan will eventually want to read from, without needing to be built to depend on it yet.

None of this needs to land at once, and it shouldn't. The honest build order is Red, Blue, and Green first, because all three read from data that already exists today with zero new instrumentation — streaks, cross-community posting, and Exchange scores are all live right now. Yellow and Purple come next, once Signal engagement and a deeper Star Day reading exist to measure against. Pink, Magenta, and Indigo follow once reciprocity, community health, and Guide usage patterns have had time to accumulate real history worth evaluating. Black and White come last on purpose — Black because it mathematically requires several other keys to exist first, and White because tenure is the one thing that can't be rushed by writing more code, it just has to actually pass.

This is a proposal, not a decision — every color, every threshold, and every reward here is a first cut meant to be argued with. The one thing this section is trying to lock in is the shape: keys as a separate, permanent, breadth-and-depth layer sitting next to Standing rather than folded into it, doors that only ever add and never take away, and an endgame that turns the platform's most dedicated people into people who get consulted, not just people with the most badges.
